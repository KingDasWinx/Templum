# Requests Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every request an agent makes of the person (questions, plans, yes/no requests) waits in one inbox per
workspace, opened from the sidebar, each with where it comes from and why it is asked; no balloon on terminals.

**Architecture:** The requests already live in `Workspace::waits` (`Waiting::Question` / `Waiting::Allow`,
crates/templum/src/workspace/waits.rs). A new model layer (`workspace/inbox.rs`) lists the current workspace's ones,
keeps the selection and builds each one's "why"; a new view (`crates/templum/src/inbox.rs`) draws the popup, reusing
the balloon's question/plan/allow parts (crates/templum/src/balloon.rs) at zoom 1 as window chrome. The balloon on the
terminal becomes a small notice; the balloon's keyboard routing becomes the inbox's.

**Tech Stack:** Rust, GPUI (gpui-fast 0.1.8) + gpui-kit 0.7.3 (pinned), serde_json for the MCP argument.

**Spec:** [docs/specs/ask-inbox.md](../specs/ask-inbox.md) (read it first; this plan argues from it).

## Global Constraints

- Only `crates/templum` depends on the UI framework; `templum-mcp` changes stay UI-free and headlessly tested.
- Every logic change ships a test that fails without it; UI-only looks: say how they were verified.
- Minors deferred go to docs/minors.md under their area; docs lines ≤ 120 columns.
- Commits on `development`, Conventional Commits; `feat`/`fix` written for someone who uses Templum.
- Before each commit, the full check:
  `cargo fmt --all && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace`.
- Theme tokens only for colors; the inbox is window chrome (never scaled by the canvas's zoom).
- The pulse runs a few seconds per new request only (no animation while requests merely wait); with reduced motion,
  none. A change to painting runs `cargo run --release -p templum -- --bench` before the PR (p95 ≤ 16.7 ms).

## Review Focus

1. A request arriving while the person types in a terminal (inbox closed, or open without the keyboard): the keyboard
   stays where it is; nothing typed reaches the inbox or is lost. → test in Task 4.
2. The selected request's block moves to another workspace, or closes, while the inbox is open: the request leaves
   this inbox (or ends), the selection goes to the next one, nothing panics. → test in Task 2.
3. A question whose client stopped waiting (`stopped: true`): the inbox shows its banner and the answer is still typed
   into its terminal. → test in Task 3.
4. Many requests (50+): the list scrolls, the badge reads "99+" past 99, the selection stays visible. → test in Task 5.
5. Two requests of one terminal: both are listed, its notice says 2, a click on the notice selects the oldest. → test
   in Task 4.

### Task 2: The inbox model: what it lists, what is selected, why each is asked

**Files:**
- Create: `crates/templum/src/workspace/inbox.rs` (registered in workspace/mod.rs)
- Modify: `crates/templum/src/workspace/mod.rs` (fields), `crates/templum/src/workspace/git_ops.rs` (`open_git`
  closes the inbox), wherever a wait ends (grep the removal of `self.waits` entries in waits.rs)
- Test: `crates/templum/src/workspace/tests/inbox.rs` (new, registered in tests/mod.rs)

**Interfaces:**
- Consumes: `Ask.why`, `Handed.text` (Task 1).
- Produces (all `pub(crate)` on `Workspace` unless said):
  - fields `inbox_open: bool`, `inbox_at: Option<u64>` (the selected wait's `key`), `inbox_focus: FocusHandle`;
  - `fn inbox(&self) -> Vec<&Wait>`: the waits whose `what` is `Question` or `Allow` and whose `from` terminal is in
    the current workspace (`self.caller(&w.from)`'s space == `self.space.id`), ordered by `key`;
  - `fn inbox_selected(&self) -> Option<&Wait>`: the wait `inbox_at` names if it is in `inbox()`, else the first;
  - `fn open_inbox(&mut self, at: Option<u64>, window: &mut Window, cx: &mut Context<Self>)`: sets `inbox_open`,
    `inbox_at` (when `Some`), closes the Git popup, focuses `inbox_focus`; `fn close_inbox(..)`, `fn toggle_inbox(..)`;
  - `pub(crate) struct Why { pub card: Option<(u64, String)>, pub task: Option<String>, pub agent: Option<String> }`
    and `fn why(&self, wait: &Wait) -> Why`: `card` = the card (id, title) of any board whose assignee is
    `Assignee::Block(uid of the asking block)` and whose column isn't its board's last, the highest id if several;
    `task` = the asking pane's `handed`'s `text`, first 3 lines; `agent` = `ask.why` for a `Question`, else None.
- When a wait that is `inbox_at` ends, `inbox_at` becomes the smallest key greater than it still in `inbox()`, else
  None (the first is then selected).

- [ ] **Step 1: Failing tests** (tests/inbox.rs), with the existing request helpers of tests/requests.rs:
  - `the_inbox_lists_this_workspaces_requests_oldest_first`: an `ask_user` from A, a `connect` from B, a `wait_for`
    from C, an `ask_user` from a terminal of another workspace → `inbox()` keys == [A's, B's].
  - `why_says_the_card_the_task_and_the_agents_words`: a board with cards #5 (Doing) and #9 (Done, last column) both
    assigned to A's block, A handed "Write the parser\nthen tests" with `why` "Need the format" → `Why { card:
    Some((5, title)), task: Some("Write the parser\nthen tests"), agent: Some("Need the format") }`.
  - `answering_the_selected_request_selects_the_next`: three requests, select the 2nd, answer it → selected is the 3rd;
    answer it → the 1st.
  - `a_selected_requests_block_moved_away_leaves_the_inbox` (Review Focus 2): move the selected request's block to
    another workspace → it's not in `inbox()`, selection is the next; close a block whose request is selected → the
    request ends, no panic.
  - `the_inbox_and_the_git_popup_are_never_open_together`.
- [ ] **Step 2: Run** `cargo test -p templum inbox` → FAIL.
- [ ] **Step 3: Implement** the interfaces above.
- [ ] **Step 4: Run** → PASS; full check.
- [ ] **Step 5: Commit** `refactor(connections): the requests of a workspace, listed with why each is asked` (no
